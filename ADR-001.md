# ADR-001: Secure persistence and deployment baseline for Flapjack

## Status

Proposed

## Context

Flapjack already has a working full-stack shape:

- React frontend
- Django/Channels backend
- PostgreSQL database
- Redis dependency for channel-layer behavior

However, the current repository state shows that the implementation is still operating with development-oriented assumptions rather than production-safe persistence and configuration.

Observed concerns include:

- hardcoded Django secret key
- `DEBUG=True`
- wildcard `ALLOWED_HOSTS`
- wildcard CORS
- hardcoded database credentials
- no documented backup/restore workflow
- no documented separation of development, staging, and production configuration
- local Docker Compose setup that should not be trusted as a production persistence strategy without hardening and verification

A more reliable operating model is required because the current database is being deleted and the project needs a durable long-term storage strategy.

## Decision

Flapjack will keep its current architectural shape for now:

- React frontend
- Django/Channels backend
- PostgreSQL as the primary relational store
- Redis as an ephemeral coordination dependency

But production persistence and deployment will be standardized as follows:

1. **Use managed PostgreSQL for production**
   - PostgreSQL remains the source of truth for durable relational data.
   - Production data must not depend on an ad hoc local container database.

2. **Use encrypted automated backups**
   - Enable scheduled backups and point-in-time recovery where supported.
   - Document restore steps and test them.

3. **Use environment-based secret management**
   - No hardcoded secrets in source control.
   - Secret key, database URL/credentials, allowed hosts, CORS origins, and related settings must be injected by environment.

4. **Keep Redis non-authoritative**
   - Redis may continue to back Channels or caching.
   - Redis must not be used for irreplaceable durable state.

5. **Use object storage for large uploaded files when needed**
   - If Flapjack stores raw uploaded assay files, exports, or binary artifacts, those should move to durable object storage rather than ephemeral container filesystems.
   - Database records should reference object storage locations when appropriate.

6. **Separate environments**
   - development
   - staging
   - production

7. **Fail fast on invalid runtime config**
   - the app should not start with missing required secrets or malformed database configuration in non-development environments

8. **Preserve the current product shape**
   - no rewrite is required to achieve the persistence goal
   - target hardening and documentation first

## Options considered

## Option A: Keep the current self-contained Docker Compose approach as the production model

### Pros
- fastest apparent path
- minimal code change
- easiest to keep working locally

### Cons
- weak operational durability
- poor secret management by default
- unclear backup posture
- higher risk of accidental data loss
- current repository settings are not safe enough for production
- places too much trust in local/container persistence details

## Option B: Managed PostgreSQL for production, Docker Compose for local development, Redis retained for websocket support

### Pros
- strongest balance of continuity and safety
- preserves the current backend/frontend architecture
- improves data durability significantly
- supports backups and restore workflows
- keeps local development simple
- minimizes rewrite risk

### Cons
- requires configuration cleanup
- requires environment separation
- requires backup/restore documentation and testing
- may require small code changes for object storage and settings management

## Option C: Rewrite the platform or replace major frameworks now

### Pros
- opportunity to modernize everything at once
- could reduce technical debt in the long term

### Cons
- highest delivery risk
- highest migration risk
- unnecessary before persistence and security basics are fixed
- more likely to break scientific workflows and downstream integrations

## Decision rationale

Option B is the best fit now.

It protects data durability while preserving the existing system shape. It is the shortest path from “working but fragile” to “maintainable and trustworthy.”

The product does not currently need a framework rewrite to achieve safe persistence. It needs:

- configuration discipline
- storage discipline
- backup/restore discipline
- documentation
- incremental hardening

## Consequences

The repository should be updated to support this decision by:

- removing committed secrets
- introducing `.env.example` files with placeholders only
- centralizing configuration parsing
- separating development and production settings
- documenting local, staging, and production runtime expectations
- adding migration, backup, and restore scripts or runbooks
- defining which data belongs in PostgreSQL, Redis, and object storage
- ensuring local Docker Compose remains a supported developer workflow

## Risks and mitigations

## Risk: legacy data may be lost during migration from the current database
**Mitigation:** define export/import steps before cutover and validate restores on a non-production environment.

## Risk: current clients depend on undocumented API behaviors
**Mitigation:** preserve endpoint contracts where possible and document intentional changes.

## Risk: object/file storage boundaries are not yet fully understood
**Mitigation:** audit upload paths before changing storage backends.

## Risk: old framework/runtime versions increase maintenance burden
**Mitigation:** stabilize persistence first, then plan dependency upgrades in bounded phases.

## Revisit triggers

Revisit this ADR if:

- production hosting constraints change materially
- websocket requirements no longer justify Redis/Channels in the current form
- the product begins storing large binary artifacts at scale
- compliance or security requirements require stronger secret or key management
- the team decides to modernize the stack after persistence hardening is complete
